# Preview aislada y transición

No se ha publicado una preview. Mantener GitHub Pages y su configuración durante la validación. La rama local y su diff requieren aprobación antes de publicar una referencia.

## Modalidad para un Supabase compartido

En Vercel configura `UDMI_PREVIEW_LOCAL=1` solo para **Preview**, con el framework **Other**, Node 24, build `npm run build` y salida `dist`. El build local carece de URL o clave Supabase, ignora los vínculos de cuenta, guarda en un espacio propio y bloquea conexiones desde la página. Comprueba `/version.json` y recorre **Mi práctica de hoy**. Para Auth, sincronización y restauración usa Supabase local desechable. La modalidad conectada descrita abajo solo aplica cuando existe un proyecto desechable separado.

La revisión de compatibilidad, el aislamiento de un esquema candidato y el plan de respaldo y reversión están en [SUPABASE_COMPARTIDO.md](SUPABASE_COMPARTIDO.md).

## Acciones del titular

1. **Aprobar el canal de distribución del commit.** Si se usará Git, publica únicamente la rama revisada en un repositorio autorizado o aprueba el push correspondiente. La alternativa es un artefacto `dist/` revisado a través de Vercel CLI desde el equipo del titular. Para publicar estáticamente mediante Git, conecta solo el repositorio requerido. Confirma que el plan del titular permite una preview de acceso restringido. Si un ajuste implica cargos, decide antes de activarlo.
2. **Supabase Dashboard → New project**. Selecciona una organización para un proyecto desechable que no sea el proyecto real. Elige el plan acordado. En SQL Editor aplica el esquema sintético en este orden: `tests/fixtures/supabase-base.sql`, `supabase/fase0-respaldos.sql`, `supabase/fase1-intentos.sql`, el SQL histórico obtenido con `git show c6cd53f:supabase/fase-cuenta.sql`, `supabase/fase2-estabilidad.sql`, `supabase/fase2-acceso-aislado.sql` y `supabase/fase15-familia.sql`, `supabase/fase2-diagnostico.sql` desde Fase 2 y `supabase/fase3-lecciones.sql` desde Fase 3 y `supabase/fase4-historial.sql` después de Fase 4. Esos fixtures se destinan exclusivamente a la preview. No aplicar ese lote al proyecto con datos reales.
3. **Supabase → Authentication → Sign In / Providers.** Habilita correo y sesiones anónimas. En **Users**, agrega una cuenta de prueba confirmada que recibirá el correo. En **Email Templates → Magic Link**, incluye el código de verificación `{{ .Token }}`, sin acortarlo, por ejemplo `<p>Tu código para entrar es {{ .Token }}</p>`. Usa un buzón o remitente autorizado. La app verifica el OTP en la misma pantalla. El servicio real de entrega de correo debe probarse desde la preview. Para crear un perfil sintético, genera un código con `replace(gen_random_uuid()::text,'-','')`, insértalo en `tt_progreso` con un JSON ficticio que contenga `pts` y guárdalo fuera de Git.
4. **Vercel → Add New → Project → Import Git Repository**. Elige la referencia revisada. Configura Framework **Other**, Build Command `npm run build`, Output Directory `dist`, Node 24. En **Settings → Environment Variables**, añade **solo al scope Preview** `UDMI_PREVIEW_SUPABASE_URL` y `UDMI_PREVIEW_SUPABASE_PUBLISHABLE_KEY` del proyecto desechable, que se obtienen en Supabase → Project Settings → API Keys. La clave comienza por `sb_publishable_`. El build rechaza una preview apuntada al origen productivo registrado. Mantén sin valores las variables de producción durante la prueba. Si Vercel exige una rama de producción al crear el proyecto, espera la aprobación de un proyecto de pruebas o usa un despliegue Preview explícito por CLI.
5. **Autoriza la preview expresamente antes de iniciarla.** En Supabase → **Authentication → URL Configuration** añade exactamente la URL de prueba con barra final. Configúrala como Site URL en el proyecto desechable si es su única app. El OTP en la misma pantalla no depende de una redirección. Las URLs permiten probar también las comunicaciones de Auth y evitan comodines en otros flujos. Elige una URL fija para el piloto y restringe el acceso a sus verificadores.
6. **Valida desde dos dispositivos de prueba.** Comprueba `/version.json` contra el SHA aprobado y que rutas de documentación, SQL y pruebas no están publicadas. Inicia sesión con el OTP recibido, vincula el perfil sintético, autoriza y reabre la app en ambos dispositivos. Simula desconexión, revocación y restauración. Guarda solo evidencia sintética y el SHA. Usa la cuenta y el código de prueba para esta verificación.

## Después de aprobar el ensayo

1. Mantener operativa la URL pública anterior. Confirmar el plan en **GitHub → Settings → Billing and licensing**. Pages desde un repo privado requiere un plan compatible. En Free, cambiar visibilidad puede interrumpir Pages. Aunque el plan lo soporte, el sitio y su backend tienen controles de acceso separados.
2. Preparar captura aprobada de cada dispositivo, lado servidor y colas pendientes. La versión antigua de Pages puede carecer del exportador operativo y una URL nueva no puede leer su almacenamiento. Tras verificar la preview, autorizar por separado una ventana de transición en el origen existente con interfaz compatible o una extracción privada de sus claves locales por el operador. Si la app anterior sigue escribiendo, confirmar que toda sincronización esté cerrada antes de conciliar.
3. Revisar el esquema real y los vínculos preexistentes antes de una migración. La unicidad por dispositivo exige detectar autorizaciones múltiples. La vinculación familiar supone un titular por perfil; vínculos preexistentes de varias cuentas se revisan manualmente. Aplicar solo los cambios aprobados y compatibles, dejando el corte desactivado. Vincular y recuperar usando el mismo perfil. Comprobar estado, recompensas, UUID y accesos en los dispositivos de la familia.
4. Comparar el inventario de dispositivos autorizados y el uso de RPC en los registros privados de Supabase. Solicitar actualización de clientes que llaman `tt_guardar` o `tt_guardar2`. Confirmar los dispositivos y preservar el progreso local de los que estén sin conexión. Solo con aprobación, invocar el corte por perfil. Las dos RPC heredadas quedarán rechazadas incluso para un adulto, y la ruta de código requerirá cuenta vinculada. El corte no está expuesto en la interfaz. Un intento de reapertura con la RPC antigua de cuenta también se rechaza.
5. Publicar el commit verificado en el dominio aprobado con las variables productivas autorizadas y `UDMI_FAMILY_AUTH=1`. Configurar Site URL y retornos exactos. Confirmar los accesos infantiles y familiares, y retirar Pages o cambiar visibilidad únicamente después. Ante un problema, revertir al artefacto de Vercel probado y compatible con el esquema. Conservar el estado nuevo y las colas. Reabrir una ruta de escritura heredada o revertir datos exige otro acuerdo.

## Alcance del ensayo

Las copias cifradas se usan con el mismo identificador de perfil y proyecto. Un navegador desconectado puede cerrar su vista de estudio y, tras recuperar conexión, abrir `?familia=1` en el mismo origen para capturar la cola sin subirla primero. Conservar el archivo y su frase por separado. Dejar en pausa los dispositivos fuente hasta confirmar recuperación y comprobante, luego reabrir para que reconozcan los UUID transferidos.

Una copia operativa conserva las filas históricas y los comprobantes del perfil. Los vínculos y dispositivos permanecen en Supabase al cambiar de dominio. Las sesiones Auth pertenecen al origen. Reautorizar un dispositivo nuevo es parte de la transición. Para una migración a **otro proyecto de Supabase** o pérdida completa de esa base se requeriría restauración administrativa de las identidades y relaciones por parte del titular. Tampoco se recuperan datos locales que se hayan borrado sin tener una captura previa. Para capturas offline solapadas, conservar la más reciente por dispositivo y comparar con el estado vivo antes de conciliar; no aplicar varias como si representaran avances independientes.
