## Persistencia y reglas de conflicto

- Una clave de almacenamiento por código y otra para práctica local. Cada registro reúne estado (incluidos ajustes, historial y retos diarios), cola, versión confirmada, base, escritura pendiente y última copia operativa local. La migración se asigna al código seleccionado anteriormente, o al espacio local. Abrir otro enlace carga su propio perfil. Las claves anteriores se conservan para recuperación manual. Web Locks evita dos escritores del mismo perfil en un origen compatible. Los navegadores sin esa API requieren una sola pestaña.
- `tt_guardar3` usa compare-and-swap exacto, versión de servidor y un comprobante UUID persistido en la misma transacción que el progreso. La aplicación guarda el snapshot y el UUID antes de enviar, reconoce la versión de ese snapshot y conserva ediciones que llegaron durante la solicitud. El reintento reutiliza el UUID. Hay pausa creciente ante errores de red, límite por solicitud y reanudación al volver la red. Si falta la RPC segura, el avance queda en el dispositivo. Los lectores antiguos que aún escriben con `tt_guardar` pueden eludir CAS. La convivencia de versiones requiere un plan de corte.
- Con base común se suman deltas de puntos, rondas y errores. Las medallas usan máximos. Los hechos por tabla respetan el límite y un fallo concurrente prevalece cuando ambos cambiaron el mismo hecho. El motor combina evidencias por conocimiento y acumula intentos, aciertos, aplicación y errores cuando la base permite hacerlo. Los indicadores que cuentan días conservan unión o máximos cuando no hay evidencia suficiente para sumarlos.
- El reto se une por fecha y actividad, incluidas palabras y frases por separado. Si ambos completaron la misma parte, prevalece la parte confirmada por el servidor; se conserva el historial de intentos. Se recompone la boleta cuando ambas ramas contienen el día. El bono de 50 se acredita una vez por día, incluida una finalización que solo aparece al combinar partes. Los puntos de dos rondas efectivamente jugadas son independientes. Las preferencias se resuelven por campo: si uno cambió desde la base se conserva ese cambio; en conflicto se usa el valor confirmado. Un reinicio concurrente conserva una copia local de lo que quedó fuera.
- Sin base común, no se suman agregados históricos que podrían duplicarse. Se unen partes e historiales y se usan máximos para totales ambiguos. El reloj local sigue presente para la fecha pedagógica y algunos desempates de datos históricos. Los intentos individuales conservan UUID, se suben por lotes y siguen pendientes cuando la RPC no existe. La respuesta SQL de inserción permite deduplicar UUID repetidos.

## Respaldo y recuperación

- La copia portable v1 contiene el progreso consolidado y filtra credenciales y campos de sesión conocidos. Una copia antigua se concilia con el avance que ya existe. Los totales ambiguos se conservan por máximo; preferencias y partes completadas equivalentes priorizan el estado actual. En un perfil vacío se puede recuperar el progreso anterior. Una copia local debe guardarse antes de restablecer o importar.
- La copia operativa une el registro local del perfil (incluidos pendientes, versión, base y comprobante) y `tt_fase2_copia` con progreso, intentos UUID, copias y comprobantes de servidor. Guardarla cifrada y fuera de Git. El prototipo de servidor la restringe a una sesión de adulto reciente y vinculada. Se debe conciliar en un entorno aislado, incluir los UUID posteriores al corte y cotejar la versión viva antes de aplicar. La exportación portable no transporta esa cola ni el historial bruto. La transmisión de los pendientes entre orígenes exige una transferencia operativa separada. Preparar una herramienta de transferencia completa y una interfaz parental de vista previa antes de habilitar recuperación operativa en producción.
- Cambio de origen: conservar Pages y cada dispositivo. La revisión actualmente publicada puede carecer de exportación. En ese caso hacer una captura privada del almacenamiento del origen existente o preparar una herramienta de recuperación autorizada. Capturar por perfil el avance sincronizado y cualquier cola local, ensayar la recuperación en el nuevo dominio con datos ficticios, validar acceso y notas en dos dispositivos, y solo entonces retirar enlaces antiguos. Conservar un corte del nuevo avance por si se revierte el frontend. Cambiar la visibilidad del repo puede afectar Pages según el plan.

## Acceso con Supabase Auth

`supabase/fase2-acceso-aislado.sql` ensaya el esquema de cuenta por correo que ya existe: el adulto vinculado con sesión reciente autoriza a un UID anónimo de Supabase Auth. El niño recibe un identificador de perfil y conserva la sesión de estudio, independiente del código heredado. El servidor comprueba una autorización por dispositivo en lecturas y escrituras. Las escrituras de estudio filtran campos administrativos, preservan los controles parentales de un reto y rechazan restablecer puntos. El contenido académico enviado por el cliente todavía requiere validación por evento antes de confiar en él. Revocar el vínculo bloquea la siguiente operación aun con JWT vigente. El registro se puede autorizar de nuevo desde la sesión del adulto.

El prototipo SQL cubre autorización, revocación, estudio, intentos y copia operativa. El HTML sigue usando los endpoints de código. Queda integrar el emparejamiento y las vistas de ambos roles, la conexión del frontend con la subida de intentos en modo de estudio, los ajustes parentales, la recuperación por correo y una restauración administrativa autenticada. Las RPC antiguas siguen disponibles para perfiles no protegidos. Validar ese límite y el cierre de accesos viejos con un piloto antes de migrar un perfil real.

- `npm run build` genera solo `index.html`, JavaScript con huella de contenido y `version.json`. Configurar `UDMI_SUPABASE_URL` y `UDMI_SUPABASE_PUBLISHABLE_KEY` por entorno. La clave se entrega al navegador y debe ser publishable. Vercel inyecta `VERCEL_GIT_COMMIT_SHA`. Revisar el SHA en `version.json` y en la ficha del despliegue. El HTML y el manifiesto se revalidan, y los JavaScript con huella usan caché inmutable.
- Para un despliegue futuro, aprobar primero integración privada, preview y URLs de retorno exactas de Auth tanto para pruebas como para el dominio aprobado. Publicar solo el artefacto `dist/` verificado. Revertir seleccionando en Vercel una compilación previamente verificada y manteniendo el backend compatible. Para Auth, configurar el dominio aprobado como Site URL y añadir las URLs exactas de retorno de producción y de cada preview autorizada. Usar un backend aislado para previews. No ampliar los patrones de retorno por comodidad. La reversión de datos es una acción aparte. No se ha creado proyecto ni se ha desplegado en Vercel. La convivencia con clientes antiguos requiere una ventana y un plan de retiro para la escritura heredada.
